**Latest reported evidence (founder's laptop terminal, reported 29 October 2026; not independently rerun by the assistant that edited this document):** `npx vitest run` passed 44 test files and 554 of 554 tests; the dedicated Phase 4C regression tests (`resetRace.test.ts` and `demoEpoch.test.ts`) passed 6 of 6; `npm run typecheck`, `npm run lint` and `npm run format:check` passed (exit 0); `npm run build` exited 0 (407 modules transformed); and `git diff --check` reported no issues. The commit and working-tree state of that run were not re-verified here. The Playwright end-to-end suite was not part of that report, so its status after the Phase 4C changes is not established (the last reported end-to-end result, 80 of 80, is from the earlier 28 October working tree).

**Test history (the earlier failure is neither a current reproduced failure nor a conclusively resolved root cause):** on 28 October 2026 one full unit-test run (496 of 496 tests passed) exited 1 because of an unhandled Dexie `DatabaseClosedError`; four other runs exited 0. That failure was intermittent and its cause was not diagnosed at the time. A reset/sync race was then identified and addressed in Phase 4C, and in the latest reported run the dedicated regression tests and the full suite passed. That does not conclusively show that the race caused the earlier error, and it does not show that every possible reset/sync failure has been eliminated. The latest result is one reported run, so the unit suite is described as passing in that run, not as proven stable.

**What Phase 4C does (demo consistency, not security):** in the mock server, state-changing operations are processed one at a time, and a request that carries the identifier of a demo epoch that has already ended (that is, one from before **Reset demo**) is rejected with a conflict response instead of being written. This keeps the demonstration consistent when a reset happens while a sync is in flight. It is a demo-consistency mechanism in a mock API, not a production security or concurrency control. Known gap (internal): there is no dedicated test for the server-only reset API path; the reset-race tests exercise the `resetDemoEnvironment()` function.

Post-review change (Phase 4A): the Overview page now shows a data-provenance line that can display an exact count of demo-created records, including 0 to 4, but only when every non-seed assessment in the view is verified as a synthetic demonstration record; otherwise the small-count rule applies to the whole figure. The GIS map and table were not changed by this, and still show counts of 1 to 4 as "n/s". Statements elsewhere in this pack that Overview counts of 1 to 4 are "n/s" predate this change. This is a prototype-specific classification of demo-created records and a display rule on synthetic data, not an authentication or security control. Publishing the baseline count beside another total could allow a hidden figure to be inferred by subtraction; this has not been comprehensively audited across combinations of views, filters and dates, and no claim is made that hidden counts cannot be reconstructed. (`artifacts/demo-evidence/PHASE4_SEED_LIVE_TRANSPARENCY_REPORT.md`, Phase 4A section).

## Required clinical and privacy language (copy into any application text)

- FGS content and rules are demonstration placeholders awaiting appropriate clinical review and validation.
- NTD-WATCH does not diagnose FGS or prescribe treatment.
- Programme priority is not clinical severity or disease prevalence.
- Community observations are not a representative epidemiological sample.
- Synthetic facility and community data do not establish real-world coverage or disease distribution.
- The current API is a mock implementation; privacy tests do not prove production-server security.
- Privacy suppression is a prototype pattern that still requires specialist review.
- The prototype applies a small-count display rule to selected published programme views and exports. This is a client-side display measure, not a security control. Unresolved: differencing across separate queries and date ranges; exact WASH percentages and the vulnerability index; staff counts; direction labels and signal bands that can narrow hidden counts; the facility referral inbox, which returns record-level data; full records held in the browser database and mock server; the threshold of 5 is a placeholder not justified by specialist review; and there has been no independent privacy review or production-security validation.
