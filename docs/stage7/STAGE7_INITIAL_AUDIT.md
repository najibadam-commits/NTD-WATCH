# Stage 7 initial audit

**Date:** 2026-10-19. **Scope:** what existed at the start of Stage 7 (the end of Stage 6) measured against the Stage 7 brief "Demo-Ready MVP & Launch Readiness". This audit was done before any Stage 7 code change. Counts come from the repository at that point (236 unit tests, 36 end-to-end tests).

## 1. Verdict in one paragraph

Stages 1 to 6 left a working, tested prototype whose **CHW experience, mock server, offline queue, programme dashboards and GIS were already real**. What it lacked was **coherence across roles**: there was no facility experience (the facility role could only see aggregate referral counts), no priority view combining the signal and vulnerability layers, no recorded facility outcome, no way for the CHW and programme views to reflect a facility action, no single reset, no rule governance screen and no honest on-screen real/simulated/future register. Stage 7 therefore extends the existing code. Nothing was rebuilt.

## 3. Findings that shaped the work

1. **The facility experience was the weakest link in the story.** A demo that shows the CHW moving the facility's status with a button does not persuade anyone that a facility worker can do it. The inbox was built on the existing mock API and role model.
2. **The demo users did not line up.** The Facility demo user's simulated scope was `fac-c1`, while the demo CHW's community refers to North LGA facilities, so a facility switch would have shown an empty inbox. The facility scope is now `fac-n1`.
3. **Seeded referrals could not be updated** because they were not stored on the mock server. A stored copy is now created on first update and preferred when records are merged, so nothing is double counted.
4. **One random stream made every community depend on all the others.** Changing one community's profile reshuffled the rest. Seed generation now uses one stream per CHW, so scenarios are stable.
5. **A hidden table header widened the page on phones.** It forced a zoomed-out layout and made controls unreachable. Found by the cross-role end-to-end test on the mobile profile and fixed once in the shared table wrapper.
6. **The product's four risk levels (LOW, MODERATE, HIGH, URGENT) are kept.** The brief speaks of low, elevated and high signals. The mapping is documented, not renamed in code, to avoid churn and keep earlier tests valid. For programme views a "signal" is the share of assessments rated HIGH or URGENT.

## 4. What the audit decided not to do

No real data, production clinical rules, DHIS2 or other live integration, real authentication, hosting, notifications, outbreak detection or AI. Those stay FUTURE and are labelled so in the application (Settings, "What is real, simulated or future") and in `INTEGRATION_BOUNDARIES.md`.
